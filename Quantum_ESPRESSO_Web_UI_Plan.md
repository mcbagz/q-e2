# Quantum ESPRESSO Web UI: A Detailed Development Plan

## 1. Vision & Goal

The primary vision is to transform the Quantum ESPRESSO (QE) user experience from a command-line and text-file driven process into an intuitive, visual, and streamlined web-based workflow. This UI will abstract away the complexities of input file generation and command execution, making QE more accessible to a broader audience, including researchers and students.

**Key Objectives:**
*   **Intuitive Setup:** Enable visual confirmation of atomic structures through 3D rendering, even if input is text-based.
*   **Simplified Workflow:** Integrate simulation setup, execution, monitoring, and post-processing into a single, cohesive web application.
*   **Abstraction:** Shield users from the intricacies of QE namelists and command-line arguments.
*   **Portability:** Deliver the entire solution within a Docker container for easy deployment and consistent environments.

## 2. Core Features

### 2.1. Project & Simulation Management
*   **Dashboard:** A central page listing all created simulations/projects with their status (e.g., "Draft," "Running," "Completed," "Error").
*   **New Simulation Creation:** A clear entry point to start configuring a new QE calculation.
*   **Load/Save Configuration:** Ability to save and load simulation parameters and structures.
*   **Organization:** Basic filtering or grouping of simulations (e.g., by user-defined tags or calculation type).

### 2.2. Simulation Setup (Pre-processing)
*   **Calculation Type Selection:** User-friendly selection of common QE calculation types (e.g., SCF, NSCF, Relax, MD, Phonon, Band Structure, DOS). This will dynamically adjust available input parameters.
*   **Interactive 3D Structure Viewer (Three.js):**
    *   **Visual Confirmation:** After inputting atomic coordinates and lattice parameters (e.g., via text fields or file upload), Three.js will render the structure in 3D.
    *   **Exploration:** Users can rotate, zoom, and pan the 3D view to inspect the structure from various angles.
    *   **Import/Export:** Support for common crystallographic formats (e.g., CIF, POSCAR, XYZ) for importing existing structures and exporting generated ones.
*   **Pseudopotential Management:**
    *   **Automated Selection:** Auto-assign pseudopotentials based on the elements present in the structure, drawing from a pre-configured library within the Docker container.
    *   **Search/Browse:** Allow users to manually select pseudopotentials from a searchable list.
*   **Input Parameters Abstraction:**
    *   **Common Parameters:** UI elements (sliders, text inputs, checkboxes) for frequently used QE parameters (e.g., `ecutwfc`, `ecutrho`, k-points grid, smearing type, degaussing).
    *   **Auto-Optimization Integration:** Checkboxes to enable automatic k-point and cutoff optimization, leveraging the `AUTO_OPTIMIZE` namelist functionality.
    *   **Advanced View:** An option to expose a raw namelist editor for expert users, potentially with syntax highlighting.
*   **Input File Generation:** Backend logic to translate all UI selections and 3D structure data into a valid QE input file (`.in` format).

### 2.3. Simulation Control & Monitoring (Running)
*   **Run/Pause/Resume/Stop:**
    *   **Run Button:** Initiates the QE simulation (e.g., `pw.x`).
    *   **Real-time Log Output:** Stream `stdout` and `stderr` from the running QE process directly to the UI via WebSockets.
    *   **Progress Indicators:** Display current iteration, total energy, and convergence status by parsing the streamed log output.
    *   **Snapshot Button:** Triggers a status snapshot during a running simulation (sends `SIGUSR2` to the QE process).
    *   **Checkpoint Button:** Gracefully stops the simulation and creates a checkpoint (sends `SIGUSR1` to the QE process).
    *   **Resume Button:** Allows restarting a simulation from a selected checkpoint.
    *   **Force Stop/Kill:** Emergency termination of the QE process.

### 2.4. Results Visualization & Analysis (Post-processing)
*   **Output Log Viewer:** Display the complete output log of completed simulations.
*   **Structure Visualization:** View final relaxed structures or animate molecular dynamics trajectories in 3D (Three.js).
*   **Automated Plotting Integration:** Leverage the `pp.x --visualize-all` feature (as per `Automated_Visualization_Plan_V2.md`) to automatically generate all possible plots from the output directory.
*   **Interactive 3D Data Visualization (Three.js):**
    *   Render volumetric data such as charge densities, potentials, and wavefunctions (from XSF/cube files generated by `pp.x`).
    *   **Layer Control:** Provide checkboxes or toggles to show/hide different data fields (e.g., charge density, spin density, electrostatic potential) or different isosurfaces/slices within the 3D viewer.
    *   Tools for slicing, isosurfaces, and contour plots within the 3D viewer.
*   **2D Plotting:**
    *   Generate and display 2D plots for band structures, Density of States (DOS), and convergence curves (energy vs. iteration).
*   **Download Functionality:** Allow users to download raw output files, generated plots, and input files.

## 3. Technical Stack

### 3.1. Frontend (User Interface)
*   **Framework:** HTML/CSS/JS static site. Vite to build bundle.
*   **3D Visualization:** Three.js (for interactive structure viewing and rendering volumetric data).
*   **UI Components:** Tailwind CSS (for highly customizable styling).
*   **Charting Libraries (2D):** Chart.js or Plotly.js (for rendering DOS, band structures, and other 2D data).
*   **Communication:** Fetch API for RESTful API calls, WebSockets for real-time data streaming (e.g., QE output logs).

### 3.2. Backend (API & QE Orchestration)
*   **Language:** Python (for its strong capabilities in scripting, process management, and data parsing).
*   **Web Framework:** FastAPI (chosen for its high performance, asynchronous support, and automatic API documentation via OpenAPI/Swagger).
*   **Process Management:** Python's `subprocess` module (for executing QE binaries, managing their lifecycle, and sending signals).
*   **File I/O & Parsing:** Python's built-in file operations, `xml.etree.ElementTree` for parsing QE's XML output files (`data-file-schema.xml`). Regular expressions for parsing text-based output logs.
*   **Data Storage:** SQLite (a lightweight, file-based database) for storing simulation metadata, user configurations, and project status.
*   **Asynchronous Tasks (Optional but Recommended):** Celery with Redis/RabbitMQ (for handling long-running QE simulations in the background, preventing API timeouts and improving responsiveness). This would be crucial if the UI needs to support multiple concurrent users or very long simulations.

### 3.3. Containerization & Deployment
*   **Docker:** The entire application (frontend, backend, QE executables, pseudopotentials, dependencies) will be packaged into a portable Docker image.
*   **Docker Compose:** Used to define and run the multi-service application (e.g., separate containers for frontend, backend, and potentially a Redis/Celery worker).
*   **Web Server:**
    *   **Backend:** Uvicorn (ASGI server for FastAPI).
    *   **Frontend:** Nginx (to serve the static site and act as a reverse proxy, routing API requests to the FastAPI backend).

## 4. Phased Implementation Roadmap

### Phase 1: Core Functionality & Basic UI (MVP)
*   **Frontend:**
    *   Basic applciation application setup.
    *   Dashboard to list simulations (placeholder data initially).
    *   "New Simulation" form with basic text inputs for `prefix`, `outdir`.
    *   Simple text area to display QE output logs.
    *   Run/Stop buttons (basic `subprocess` calls).
*   **Backend:**
    *   FastAPI application setup.
    *   API endpoints for:
        *   Listing simulations.
        *   Creating new simulation entries.
        *   Starting/stopping QE processes (using `subprocess`).
        *   Streaming QE output logs via WebSockets.
    *   Basic input file generation (hardcoded parameters for a simple SCF calculation).
    *   QE binaries and pseudopotentials integrated into the Docker image.
*   **Docker:** Initial `Dockerfile` and `docker-compose.yml` to get the basic stack running.

### Phase 2: Structure Viewer & Input Parameter Abstraction
*   **Frontend:**
    *   Integrate Three.js for a basic 3D structure viewer (rendering structures from text input).
    *   Implement tools for rotating, zooming, and panning the 3D view.
    *   UI elements (sliders, dropdowns) for `ecutwfc`, `ecutrho`, k-points grid.
    *   Pseudopotential selection UI.
*   **Backend:**
    *   Enhance input file generation logic to handle dynamic structure data and more parameters.
    *   Implement pseudopotential scanning from a designated directory.
    *   Integrate `AUTO_OPTIMIZE` namelist generation based on UI checkboxes.

### Phase 3: Advanced Simulation Control & Monitoring
*   **Frontend:**
    *   Real-time progress indicators (parsing log output).
    *   Snapshot and Checkpoint/Resume buttons.
*   **Backend:**
    *   Implement robust `subprocess` management for long-running QE processes (handling `SIGUSR1`, `SIGUSR2`).
    *   Logic for parsing QE output logs to extract progress information (energy, iterations, convergence).
    *   Implement checkpoint loading and resuming.
    *   Consider integrating Celery for background task management if responsiveness becomes an issue.

### Phase 4: Post-processing & Visualization
*   **Frontend:**
    *   Results dashboard for completed simulations.
    *   Integrate Three.js for 3D volumetric data visualization (charge density, potential) with layer control (show/hide different fields).
    *   Implement 2D charting for DOS and band structures.
*   **Backend:**
    *   Integrate the `pp.x --visualize-all` functionality (from `Automated_Visualization_Plan_V2.md`).
    *   API endpoints to serve generated visualization files (XSF, cube, 2D plot data).
    *   Logic to parse `data-file-schema.xml` to determine available plots.

### Phase 5: Refinement, Usability & Robustness
*   **Frontend:**
    *   Improve UI/UX based on user feedback.
    *   Comprehensive error display and user guidance.
    *   Input validation.
*   **Backend:**
    *   Robust error handling and logging.
    *   Security considerations (if exposed to multiple users).
    *   Performance optimizations.
*   **Documentation:** Comprehensive user and developer documentation.

## 5. Key Challenges & Considerations

*   **QE Output Parsing:** QE's output formats can be complex and varied. Robust parsing logic is crucial.
*   **Real-time Data Streaming:** Efficiently handling and displaying large volumes of log data over WebSockets.
*   **Resource Management:** QE simulations are computationally intensive. The Docker environment needs to be configured with adequate resources.
*   **Error Handling:** Translating cryptic QE errors into user-friendly messages.

This plan provides a solid foundation for building the Quantum ESPRESSO Web UI. It breaks down the complex vision into manageable phases and outlines the necessary technical components.
